# Enriquecimento da geração

A geração base (`CvPipeline`) usa só os fatos aprovados e a IA apenas escolhe ordem e densidade. O enriquecimento acrescenta uma etapa opcional para o currículo ficar mais completo e pontuar melhor no ATS, sem perder a verdade dos fatos: evidências complementares confirmadas pela pessoa e reescrita com âncoras. As regras abaixo valem para o que está implementado; a lista **Estado atual** diz o que ainda falta.

- **Fontes:** links já presentes nos fatos aprovados (ex.: repositórios de projetos), busca web, notas do vault Obsidian (second brain), quando configurado, e os repositórios públicos do GitHub da própria pessoa (veja abaixo).
- **Evidência complementar:** cada detalhe encontrado vira uma evidência com fonte (URL ou caminho da nota), trecho citado, data de coleta e estado de revisão (`pendente`, `confirmado`, `descartado`). Evidências ficam ligadas ao snapshot do Ground Truth e, após o uso, à geração. Elas não são fatos do Ground Truth e não alteram o snapshot.
- **Revisão:** antes de gerar, a pessoa confirma ou descarta cada evidência. Só as confirmadas podem entrar no currículo.
- **Reescrita com âncoras:** a IA pode reescrever bullets, reordenar e adaptar vocabulário à vaga. Cada bullet gerado deve citar os IDs de fatos ou evidências confirmados que o sustentam; um verificador determinístico remove o que não tiver âncora e registra o descarte no relatório da geração.
- **Templates e padrões do perfil:** `modern-v1` (acento de cor nos títulos), `editorial-v1` (serifado, títulos em itálico) e `harvard-v1` (formato Harvard: nome centralizado, seções em versalete, datas à direita) já existem. O layout padrão é definido no perfil (`CvPreferences.templateName`) e fica salvo na conta (`GET/PUT /v1/owners/{ownerId}/generation-defaults`, tabela `owner_generation_defaults`); no gerador a pessoa troca o layout só para a vaga em andamento, sem alterar o padrão. Sessões anônimas não salvam. A mesma rota guarda os demais padrões do perfil: `optimizeForAts` (otimiza o layout até a nota de ATS ficar boa; ligado até a conta desligar, e só no perfil para contas) e `guidelines` (diretrizes de destaque, lista inteira, V23). O gerador parte desses padrões e permite ajustar diretrizes e layout por vaga sem gravar na conta; se a requisição de geração vier sem `preferences`, o servidor os usa. Os três mudam só a apresentação; texto, ordem e fatos são os mesmos. Ainda não há fonte sem serifa embutida no renderizador, então os layouts usam a Libertinus.
- **Exclusão:** evidências são apagadas junto com o snapshot ou a geração que as originou.

## Estado atual

- Implementado: base de dados (`V13__cv_supplementary_evidence.sql` e `V14__cv_evidence_link_checks.sql`), modelo `SupplementaryEvidence` e coleta a partir dos **links já presentes nos fatos aprovados** (`POST /v1/cv/evidence/snapshots/{snapshotId}/collect`, `GET /v1/cv/evidence/snapshots/{snapshotId}`). A coleta baixa a página com o mesmo buscador de vagas (política anti-SSRF, limites de tamanho e de redirecionamento), pede à IA detalhes com trecho literal, descarta os trechos que não existem na página e grava cada detalhe como `pendente`. Sem provedor de IA, nada é coletado; no máximo 5 links por chamada; cada link analisado consome uma unidade do limite de processamento do visitante (contas não têm limite); links já analisados (`cv_evidence_link_checks`), mesmo sem detalhes, não são analisados de novo.
- Implementado: revisão na interface. `PATCH /v1/cv/evidence/{id}/review-state` confirma, descarta ou devolve a `pendente` uma evidência. Ao clicar em gerar, contas buscam evidências novas (`POST /v1/cv/evidence/snapshots/{id}/collect`; fontes já analisadas são puladas, então repetir é barato). Se houver evidência `pendente`, o mesmo diálogo de revisão antes de gerar passa a incluí-las, com o trecho original ao lado de cada detalhe, e a geração só segue depois; pendente não bloqueia, apenas fica fora do currículo. Falha ou limite na busca não impede a geração. Sem evidência pendente nem pendência de fatos, gera direto. Não há mais card de evidências nas etapas do gerador: o rodapé da geração mostra um resumo e abre a lista para mudar decisões ou buscar novas. Visitantes anônimos não têm essa etapa, porque o snapshot ativo só é conhecido pela conta.
- Implementado: reescrita de conteúdo na geração (`CvContentEnricher`, pipeline `cv-pipeline-6`). As diretrizes de destaque do gerador chegam à reescrita (`CvContentEnricher.emphasis`) e ao planejamento de layout; só decidem o que pôr em primeiro plano entre fatos já citados, e são ignoradas onde as fontes não as sustentam. A IA reescreve as frases de **experiência e projetos** e o **resumo** (só se já existir um resumo aprovado), com o vocabulário da vaga, em uma única chamada. Cada frase precisa citar as fontes que usou e passa por `BulletVerifier`, que rejeita frase sem fonte, número que não está nas fontes citadas e nome próprio (ferramenta, empresa) ausente delas. Fontes de um item: título, empresa, período, descrição aprovados e, em projetos, as evidências confirmadas ligadas ao link; o resumo só se apoia no próprio texto, no título profissional, nos cargos e nas tecnologias. Um item mantém o texto aprovado quando nenhuma frase passa, quando a reescrita perderia um número do texto original (métricas não se perdem) ou quando só tem título e período, sem descrição nem evidência (nada a reescrever). O resultado (frases aceitas e rejeitadas, evidências usadas, se o resumo foi reescrito) fica em `tailoring.enrichment`. Sem IA, nada é reescrito.
- Implementado: apresentação mais enxuta (`cv-pipeline-6`). Cada linha de descrição, incluindo métricas ("Resultado: …"), vira um **bullet** de lista nativa no PDF e no Markdown, sem marcador duplicado. Com 5 ou mais tecnologias, `TechnologyGrouper` as **agrupa por categoria** ("Backend: Java, Spring Boot."; "Banco de dados: PostgreSQL, MySQL."), com um dicionário determinístico: cada tecnologia aparece uma vez, com o nome aprovado, e o que o dicionário não conhece vai para "Outras", nunca é descartado. Listas curtas sem ordem de leitura relevante (idiomas, tecnologias soltas) saem numa linha só separada por "·". A regra de uma coluna continua valendo para o que muda a ordem de leitura (experiência, formação, projetos); agrupar em linhas rotuladas ou juntar itens curtos não introduz colunas, tabelas nem caixas. Planejado: usar a IA para categorizar tecnologias fora do dicionário.
- Implementado: três fontes de evidência sobre os itens do snapshot, **projetos (com ou sem link) e experiências** (`EvidenceSubjects`; cada evidência guarda a chave do item, ex.: `projects:2`, e o enriquecimento casa por ela, não só pelo link). (1) Links já presentes nos fatos aprovados. (2) Busca web sobre cada projeto (título + contexto) via SearXNG local e gratuito (`services/searxng/settings.yml` e serviço `searxng` no `compose.yaml`, em `127.0.0.1:8888`; habilitada com `TAILORLY_SEARXNG_URL`, por padrão no perfil `local`); a página só conta se citar o projeto pelo nome (título ou repositório). Experiências não são buscadas na web, porque páginas sobre uma empresa não provam o que a pessoa fez nela. (3) Notas do vault Obsidian da própria conta (second brain): para cada item, as 3 notas que mais citam seus nomes (título, repositório, empresa), lidas só dentro da pasta do vault definido pela conta (`OwnerVaultService`, `VaultLocations`); só as passagens em torno da citação vão à IA, não o começo da nota. A extração (`evidence-extract-2`) recebe o item como assunto e ignora o resto do texto; o trecho de cada detalhe precisa existir no texto original. Contas têm orçamento maior por chamada (12 análises e 6 buscas) que visitantes (5 e 3); buscas e páginas irrelevantes ficam marcadas e não se repetem. As preferências da conta (pasta do vault, leitura das notas, exportação dos currículos, subpasta de exportação e busca web) ficam na seção Second Brain do perfil (`GET/PUT/DELETE /v1/owners/{ownerId}/vault`). No enriquecimento (`cv-pipeline-6`), até 6 evidências confirmadas por entrada servem de fonte para as frases de projetos **e experiências**. No gerador, o card mostra só o resumo (pendentes, confirmadas, itens) e "Revisar evidências" abre um diálogo com as evidências agrupadas por projeto ou empresa, a origem de cada uma e "Confirmar pendentes" por grupo. A coleta roda sozinha, em segundo plano, logo depois de aprovar o Currículo Base (só para contas); falhas são silenciosas e "Analisar links" continua disponível. Nada entra no currículo sem a confirmação da pessoa. Migration V21 (`subject_key`, `subject_label`); evidências antigas continuam casando pelo link.
- Verificado: o container `searxng` sobe com `docker compose up -d searxng` e `curl 'http://127.0.0.1:8888/search?q=teste&format=json'` devolve resultados em JSON. A integração Java com a API de busca (`SearxngWebSearchClient`) não foi testada contra o container numa execução completa.
- Ainda não implementado: reescrita de formação, certificações e voluntariado (listas factuais, sem prosa a reescrever) e geração de resumo para quem não tem um aprovado. Sessões anônimas escolhem o layout só no navegador.
- Implementado: **projetos candidatos do GitHub** (`GithubRepoScout`, `sourceKind = github`, V26). Para contas com o campo GitHub nos fatos aprovados e a busca web ligada no perfil, a coleta (`POST /v1/cv/evidence/snapshots/{id}/collect?jobPostingId=…`, chamada ao clicar em gerar com a vaga já lida) lista os repositórios públicos pela API do GitHub (host fixo; o usuário vem validado dos fatos; token opcional em `tailorly.github.token` para elevar o limite de requisições), descarta forks, arquivados, o repositório de perfil, repositórios de configuração e os que já estão no Currículo Base, e ordena pelos termos da vaga no nome, na descrição, nos tópicos e na linguagem (estrelas e atividade recente só desempatam). Até 3 repositórios por chamada têm o README e os metadados analisados pelo mesmo extrator (trecho literal obrigatório) e viram evidências **pendentes** de um projeto novo (chave `github:repo`); cada repositório é analisado uma vez por snapshot. No diálogo de revisão, a pessoa confirma ou descarta. Só os confirmados viram uma entrada de projeto na geração (veja [geração](cv-generation.md)). A API do GitHub sem token tem limite baixo: se falhar, a coleta segue sem os candidatos. Visitantes anônimos não têm essa etapa.
- Planejado: a IA pesquisar projetos fora do GitHub (GitLab, portfólio) e usar o README completo, não só o começo, para detalhar o projeto.
